# stage-tamagotchi

Electron desktop surface for Alicization.

## Product Experience Checks

`scripts/life-acceptance/life-product-regression.cjs` walks a fresh synthetic identity through onboarding, model confirmation, desktop model selection, card file import, memory tabs, initiative settings, backup creation, provider configuration pages, native tray handlers, actual dialogue, and chat export/import. Run it through `run-private-desktop.ps1` with a bounded child job. It uses the configured dialogue service only for synthetic QA content and removes copied credentials on exit.

The interactive `life-product-audit.cjs` captures rendered controls and screenshots for exploratory checks. Both workflows stay on an independent Windows desktop. They do not validate physical microphones, speaker quality, third-party accounts, or the user's input desktop.

## What It Does

Phase 1 life authority remains in the desktop main process. Enduring personality changes use reviewed, source-backed persona proposals; mood and busy-host withholding never directly change temperament. Personal interests are derived from verified authored projects, with evidence withdrawal and restart persistence. Daily rest/stretch shares the initiative owner and stops on host input, active execution or suspension.

Windows execution uses a sandboxed browser owned by the active card and scoped UI Automation observations of native windows. Mutations require a fresh target; destructive, transmitting, password and explicit executable actions use the existing permission UI. Unknown side effects cannot be replayed under a fresh action ID. Goal completion compares a declared text/field requirement against a second observation, or independently verifies file bytes; it never proves later external persistence from a click alone.

Speech requests carry their own delivery rate and cancellation signal. Silent visemes release old audio state; default VRM gestures have semantic joint and hand-height checks. The acceptance scripts use a muted private Windows desktop, synthetic identity and identified package bytes; they do not establish physical voice quality, multiweek companionship or Default-desktop compositor behavior.

Reply grounding presents short references limited to that review. They map back to exact ledger identities and generations before domain admission; unknown references, wrong kinds and wrong versions remain invalid. Audit receipts preserve the original reference and its canonical mapping, so a successful tool cannot manufacture a goal completion.

VRM playback preserves the native action identity and releases it on completion. Frame stalls cannot skip an entire short gesture; a bounded animation step keeps its intermediate poses visible. Native acceptance measures rendered bones and actual hand height independently from a requested cue label.

- Runs the desktop Alicization experience.
- Hosts the main-process Alicization runtime, renderer, screen-capture helpers, and desktop sensory loops.
- Is the correct app target when debugging desktop-only behavior such as proactive perception, IPC, screen capture, and TCC permissions.

pnpm -F @proj-alicization/stage-tamagotchi life:acceptance --report-only <absolute-vitest-json> --native --configured-model --installer

The first command runs desktop service coverage and shared expression checks and maps passing suites to all eighteen nodes in `output/life-acceptance/nodes.json`. The optional native run creates separate QA identities and checks persona submission, saved rhythm settings, backup creation and cancellation, Live2D/VRM pixels in the Windows compositor, blank-area input transparency, real configured-model recovery, audio completion and interruption. Its speech adapter uses actual Windows SAPI output through the production speech pipeline; it does not assess a cloud voice's quality. `LIFE_QA_EXE` selects a packaged executable. `LIFE_QA_PYTHON` selects Python for receipt queries.

Optional real-model persona/policy evaluation uses `LIFE_QA_CONFIGURED_GROWTH=1` with the two `life-*-development-runtime.test.ts` suites. It saves paired answers over synthetic fixtures and retains the candidates for review. These fixtures do not constitute a user's approval or long-term persona quality evidence.

Provider credentials may specify `contextWindowTokens`, `maxOutputTokens`, and `completionTokenField` (`maxTokens` or `maxCompletionTokens`). The final request reserves the same output limit actually sent to the provider, including tool schemas and complete message groups. Unknown context capacity uses an explicitly recorded conservative default of 65,536 with a 4,096 output reserve and a 1,024 safety reserve; configure a smaller local model's actual capacity. UTF-8 byte budgeting is an upper bound, not a claim to use the provider's exact tokenizer.

The Windows body rebinds its initial transparent native surface once after mounting. Mouse hover never repeats this transition; ordinary blur keeps the body painting, and explicit hide/minimize pauses expression. Lifecycle and native compositor results are separate from WebGL pixel witnesses.

Fresh background replies open a bounded caption presentation window. Text receipts require an expanded panel with visible viewport geometry; layout that is initially empty gets bounded animation-frame retries. The actual minimize button and collapsed orb preserve the dialogue, and speech interruption stops lip sync without falsely completing delivery.

The Codex executor inherits only the selected provider's authentication and the user's existing Windows sandbox mode. This route is covered by unit checks and actual local CLI execution; it does not copy the user's credential files into QA identities.

`scripts/life-installer-qa.config.ts` gives installer acceptance a distinct app ID, package name, GUID and shortcut policy. `scripts/life-acceptance/life-current-installer.cjs` installs it into a new temporary directory, initializes an actual QA SOUL/SQLite identity, uninstalls it, and verifies those bytes survive. ## When Not To Use It

- Do not use this app to validate web-only behavior.

## Local macOS TCC-Stable Flow

Use the installed local app flow instead of running the raw packaged bundle:

```bash
pnpm -F @proj-alicization/stage-tamagotchi build:mac:local
```

This does three things:

1. Builds the unpacked macOS app.
2. Installs a stable local bundle at `~/Applications/Alicization Local.app`.
3. Re-signs that installed bundle with a stable signing identity.
4. Automatically repairs stale macOS `ScreenCapture` / `Accessibility` TCC entries when the local build signature changed in a way that macOS can treat as a different app.

Identity selection order:

- Prefer an existing `Apple Development` or `Developer ID Application` identity if one is available.
- Otherwise create a persistent local signing identity inside `~/Library/Application Support/com.tohoqing.alicization/local-signing`.

Why the auto-repair exists:

- Local self-signed development identities do not carry a stable Apple Team Identifier.
- On macOS, `Screen Recording` and `Accessibility` grants can stay pinned to an older code requirement for that bundle id.
- After a rebuild, the app may still look toggled on in System Settings while `tccd` silently rejects the current binary as an older program.
- The installer now stops the running local app, refreshes the installed bundle, and resets the stale TCC entries when that kind of signature drift is detected.

The local flow now self-heals older broken ad-hoc/local-signing state:

- If the dedicated local signing keychain exists but does not expose a valid codesigning identity, the installer recreates that dedicated keychain and reissues the stable local certificate.
- The dedicated local keychain is added to the user search list so `codesign` can keep resolving the same identity across refreshes.

After the first install, refresh the installed bundle without changing its local identity:

```bash
pnpm -F @proj-alicization/stage-tamagotchi refresh:mac:local
```

If the refreshed local build changed and the installer auto-repaired TCC, reopen `~/Applications/Alicization Local.app` and re-enable:

- `Screen Recording`
- `Accessibility`

If the installed local app is already present but macOS is still acting like the old permission grant is stuck, repair the installed bundle directly without rebuilding:

```bash
pnpm -F @proj-alicization/stage-tamagotchi repair:mac:local:permissions
```

If you need to clear a broken Screen Recording grant from older ad-hoc builds once, use:

```bash
pnpm -F @proj-alicization/stage-tamagotchi exec tsx scripts/install-local-mac-app.ts --reset-tcc
```

Then reopen `~/Applications/Alicization Local.app` and grant Screen Recording plus Accessibility again one time.

## Validation

After granting permission, verify from runtime logs or audit logs that inspection turns no longer fall back to:

- `screen-capture-permission-denied`
- `inspection-grounding-skipped`

Expected healthy path:

- `inspection-grounded`
- or at worst `perception-only` fallback without repeated permission prompting
