# 执行层审阅：距离可靠的本地数字生命还缺什么

日期：2026-10-18。范围：当前工作区的桌面主进程执行链、Windows 浏览器与 UIA 适配器、任务与责任存储、目标核验、恢复、程序经验及身体投射。

本轮是源码审阅，没有重新运行 GUI 场景，也没有修改生产实现。本文把能够从代码直接确认的缺口与需要真实应用场景验证的判断分开。上一轮 1,435 项回归和 Live2D 定向体验只证明其声明范围内的改动，不证明整个执行层已经闭环。

## 判断

当前系统具有可用的执行基础：主进程有统一工具注册、真实任务线程、执行事件、权限接口、取消信号、落库、文件独立读回及界面复查，也会区别执行器结束和目标被证实。危险操作不应通过移除这些边界来获得所谓主动性。

最大的不足是：复杂日常目标还没有贯通成一个可持续的责任对象。目标验收不完整、执行经验的准入又偏宽，遇到平台缺项或未知副作用时，恢复路径无法稳定地把她带回同一个目标。身体目前能反映工作阶段，但对具体操作和注意对象表达较少。

## F1：Windows 键盘工具已经暴露，实际没有对应实现

**直接确认，P1。** `turn-os/tool-registry.ts:460` 注册 `desktop_press_keys`，`runtime.ts:3061` 附近把 `localBrowserAutomation.pressDesktopKeys` 接入本地执行表面；但 `local-browser-automation.ts:2141` 的实现仅支持 darwin，其他平台直接返回 unsupported。Windows UIA runtime 的返回接口也没有键盘方法。

影响：Windows 中 `Ctrl+S`、`Tab`、`Escape` 等动作无法通过这个工具完成，不能凭工具存在推断快捷键能力可用。UIA 的原生输入还拒绝隐式 submit，要求明确点击提交控件，这个约束本身应保留。

修复：先让能力清单反映平台与操作级就绪状态，再实现绑定窗口、进程、desktop 和当前观察的键盘路径。区分能够后台作用于指定控件的操作和确实需要前台输入的操作，后者必须进行焦点仲裁。

验收：真实 Windows 自有编辑器完成输入、保存、重开读回；Tab 与 Escape 到达指定窗口；用户切换窗口、目标退出或窗口身份变化时不把输入送到其他应用。所有 GUI 试验继续在私有 desktop 中执行。

## F2：普通任务默认没有机器可核验的完成标准

**直接确认，P1。** `life-task-repository.ts:27` 把新任务默认映射为 `user-reported` 证明；只有显式的 `metadata.goalProof` 才会替换。普通规划入口 `task-thread-governor.ts:184` 主要生成目标文本、通道选择和风险元数据，没有统一编制验收条件。`life-task-verification-runtime.ts:11` 的自动核验只处理 file 与 setting。

后果不是系统直接把所有线程伪装成成功：当前责任层会保留 verifying，这一点是正确的。问题是普通 Codex、CLI、浏览器或桌面长任务经常缺少把 verifying 推进到有证据完成的路径。

现有特殊闭环必须承认：直接文件写入有 `life-file-action-closure.ts` 的独立字节读回，界面有 `life-interface-action-closure.ts` 的第二次观察，个人作品也绑定了明确的文件证明。这些不能替代一个复杂任务的整体验收。

修复：在执行前把用户目标转成有版本的验收契约，明确输出物、内容要求、数量、位置、持久性、允许的影响和哪些项目需要用户评价。子动作证明必须回连到同一根目标。将“文件字节一致”“内容符合要求”“用户满意”保留为不同事实。

验收：多文件任务少一个产物、保存到错误位置、内容不符合要求、页面只显示成功但未保存，均不能完成根任务；已有正确结果可以在独立检查后避免重复操作。

## F3：尚未通过目标核验的执行，会参与成功经验选择

**直接确认，P1。** `executor-runtime.ts:595` 的程序经验构建在 `:610` 只筛选 `thread.status === 'completed'`，随后提取执行事件、结果摘要和 preferredChannel；没有要求关联责任 fulfilled、独立验证 satisfied，也没有把当前 attempt 的身份作为执行事件查询条件。`:1298` 把这些 trace 交给下一次规划。`claw-fabric.ts:231` 起会根据这些经验影响通道选择。

同一代码库已经明确规定 completed 线程对应 verifying 责任，因此这里的成功经验标准比目标完成标准宽。当前能确认的是它会影响后续路由，不能据此声称每条 trace 都已经写成长期技能或污染了人格训练。

修复：成功方法必须绑定 task、attempt、obligation generation、独立验证与来源状态；未经核验的回执只能作为待核验经历。失败经历可以保留为避坑证据，不能转成成功偏好。事件必须按 attempt 分组，避免混合旧尝试。

验收：执行器返回 completed 但独立验证失败、源证据撤销、旧 attempt 成功而当前 attempt 失败时，不产生成功方法偏好；真实验证通过后才进入相应候选。

## F4：界面风险判断偏重按钮文字和传统表单

**规则范围可直接确认；漏判场景尚未做实际应用复现，P1。** `life-interface-risk.ts:14` 主要按 label 的中英文关键词、password 和 externalSubmit 分类。`life-windows-browser-runtime.ts:167` 的外部提交识别主要覆盖表单 submit 控件与显式 submit。

“继续”“完成”“确认”等中性按钮可能通过 JavaScript 完成发信、付费或上传；输入也可能触发自动保存。当前这些语义不能仅从标签或 formAction 得到保证。本文不把这一推断冒充已经复现的付款或外传事故。

修复：把任务授权、具体目标、数据敏感性、当前页面/窗口上下文、操作效果和证据一起用于风险决策。受管浏览器可以增加可审计的外部副作用约束。普通本地动作继续默认可用，危险效果要求绑定具体内容和目标的授权。

验收：本地模拟页面以中性按钮触发外部写入、输入后自动发送、授权等待期间目标或提交内容变化，均被正确识别或中止；普通本地输入与导航不增加无意义确认。

## F5：复杂目标仍主要依靠单轮工具循环和建议动作串接

**架构范围直接确认，P1。** 主聊天 EventLoop 的模型步数为 16（`main-chat-background-run.ts:1237`），耗尽后以 timed-out 终止（`turn-os/event-loop.ts:1204`）。`task-thread-governor.ts:184` 的 plan 重点是选执行通道。局部 GUI 工作流确实能复查和继续，但 `executor-adapters/local-visual.ts:1392` 主要在 suggestedActions 之间推进、遇到等待用户或步数上限停止。

系统有事件和检查点，不应称为没有持久化；目前欠缺的是通用目标工作流：可持久化的子目标、依赖、各步验收、尚未完成的部分、恢复入口和可更新的计划版本。

修复：保留有界执行窗口，在其上增加同一责任下的工作计划。到预算边界应形成可恢复的检查点；重规划只修改未完成部分，保留真实完成证据。不要简单取消步数和时间上限。

验收：超过 16 次模型动作的工作可以分段接续；半途纠正需求后仅重做受影响步骤；重启、断网或进入等待用户状态后，恢复同一目标且不重复已完成的有副作用动作。

## F6：浏览器与原生电脑能力离真实日常应用还有明显距离

**实现范围直接确认，P1。** Windows 的 `local-browser-automation.ts:649` 进入自有 Electron browser，`life-windows-browser-runtime.ts:37` 使用独立持久化 partition，并在 `:43` 拒绝新窗口。它不能直接等同于用户已经打开并登录的 Chrome/Edge。

`life-windows-browser-page.js` 的观察主要遍历顶层 document 的控件，并限制数量；输入实现拒绝 file input，没有文件上传、iframe/Shadow DOM 遍历、通用 select、拖放或真实指针手势的完整路径。点击使用 DOM click，不能据此推断所有要求受信任输入的网站都会接受。Windows UIA 侧能做控件定位、输入及部分 Invoke/Toggle/Select，但不是完整的鼠标、键盘和视觉操作身体。

修复：明确区分自有浏览器、已授权现有浏览器和原生窗口；逐项声明操作能力及限制。优先语义化控件路径，视觉兜底也须绑定新鲜截图和窗口身份。上传、下载、文件选择与弹窗应成为完整能力，而非只把建议传回模型。

验收：真实本地网页的 iframe、滚动列表、下拉框、文件选择和新窗口流程；真实 Windows 应用中的菜单、保存弹窗和无可访问控件的界面。每类测试清楚标明当前能力支持还是明确不支持。

## F7：未知副作用能被拦住，通用恢复和补偿仍不够

**直接确认，P1。** `life-turn-runtime.ts:158` 的启动恢复会把 dispatched 效果置为 uncertain，把未结算输入置为 held。这比盲目重放正确。`executor-runtime.ts:1483` 的恢复主要是只读调查与摘要式指令；OpenClaw 没有相同的恢复派发，CLI 也不在该恢复构建器的已实现分支中。`life-contracts.ts:7` 的 compensation 只有 none/manual-review。

个人作品已有更具体的文件核验和恢复；普通多步骤桌面工作还缺少共同的“发现哪些效果已发生、确认未发生哪些、恢复到哪个安全点、如何继续”的执行协议。

修复：为能力定义只读 reconciliation、效果证据、可逆操作的备份或反向操作、无法撤回的动作及其用户处理说明。取消应停止后续行为，并如实交代已发生的影响；不能把取消等同回滚。只读恢复核验通过后，继续原目标仍需遵守原来的风险边界。

验收：写入后进程终止、点击后没有回执、部分文件已写好、发送请求超时等场景，先判断现实状态，再续做未完成部分；不可证实时保持 unknown，不能自动重复发送或付费。

## F8：主动执行尚未覆盖普遍的日常责任

**实现范围直接确认，P2。** `autonomy-actuation.ts:314` 至 `:321` 的通用主动任务派发要求 codingLike，生成的任务主要为 codebase-investigation 或 codebase-edit。另有独立个人创作、提醒和节律能力，不能说完全没有主动行动；但这些并不等于能持续履行任意日常委托。

例如整理资料、跟进一个长期学习计划、维护某份文档、在用户允许的范围内完成一个跨应用事务，需要统一的责任选择与继续工作机制。

修复：让目标和责任成为主动工作的候选来源。明确收益、授权范围、用户忙闲、资源成本和可中断点；分开决定“能否安静做事”和“是否现在打扰用户”。人格影响做事偏好与取舍，不应覆盖事实和权限。

验收：未完成的授权任务在合适时机继续；用户忙时可以安静处理允许的后台工作；暂停、取消或新需求发生时让路；没有新证据时不重复开启同一任务。

## F9：经验、技能注册和实际熟练度之间还缺一道闭环

**直接确认现有数据形态，完整技能学习能力不足属于架构判断，P2。** `memory-procedural-abstraction.ts:6` 和执行 trace 已保存方法、步骤、失败点及修复经验；`turn-os/skill-registry.ts` 也有候选、评估、激活和回滚状态，不能称为没有技能系统。但在所审路径中，经验主要提供摘要、提示和选通道依据，没有一条统一流水线保证一次做事经验变成经过复跑的可迁移技能。

修复：从有证据的成功与失败中生成可审阅的技能候选，带适用条件、参数、先决条件、效果、验收、失效条件和版本；在隔离环境用不同输入复跑，再评价是否比原方法可靠。页面或应用变化后应降级或撤销。

验收：同类任务换文件、换输入、换应用版本后仍可完成；不重复同一已知失误；不适用的旧技能会被拒绝而不是硬套。衡量完成率、返工率和对用户的打扰，而非记住的文本条数。

## F10：执行过程的身体表达主要还停留在阶段映射

**直接确认，P2。** `life-execution-presence.ts:61` 从任务/目标状态派生 phase，`:72` 映射为 concerned、hesitant 或 attentive，`:73` 固定 scenario 为 coding。当前 activity 包含任务、attempt、阶段和时间，未包含当前操作的观察对象、操作方式或具体注意目标。

已有投射防止未经验证就显示完成，也避免进度反复触发大动作，这些应保留。进一步的生命感需要让她表达“在读、在比较、在等窗口、遇到阻碍、检查结果”，并知道注意的是哪个对象；同一工作阶段不应只剩统一的忙碌动作。

修复：由真实执行事件提供有来源的注意对象和有限行动阶段，交给已有身体协调器做视线、表情、小动作与对话打断的仲裁。无新语义事件不重复播放动作。身体不能展示执行流尚未确认的成功。

验收：读取、比较、等待、受阻、复核与完成对应同轮真实事件；目光目标变化可解释；聊天插入和停止任务后恢复自然待机；执行失败和未知状态不会出现庆祝完成。

## 建议实施顺序与完成标准

1. 修正能力清单与 Windows 必需操作，补上执行前验收契约，并收紧成功经验准入（F1–F3）。先让她准确知道能做什么、何时算做完、何时算学会。
2. 补齐动作效果授权、浏览器/Windows 常见工作流和未知结果恢复（F4、F6、F7）。用真实应用阻碍验证，不只检查 mock 回执。
3. 在已有 TaskThread、LifeObligation 和 EventLoop 上实现持久工作计划及预算边界接续（F5），保留同一人格和责任所有者。
4. 让主动调度、程序技能和身体注意对象消费同一份已验证任务事实（F8–F10）。

建议用以下完整场景检验成果：用户给出一个含多个产物的委托；她明确目标和边界，选择可用通道，完成部分工作；用户中途改要求或停止，应用随后重启；她独立检查哪些结果已存在，接续剩余工作，核验全部验收项后交付；下次相似工作能复用已验证的方法。任何阶段都能解释当前进度、未知项和已经发生的影响，身体和对话表达同一事实。

只有这条场景在真实 Windows 与 Live2D 桌面上可靠通过，才有理由进一步声称执行能力支撑了持续的数字生命。
