# Upload method transfer: implementation and evidence boundary

This extends EX17's learned-method path without creating a second agent or
bypassing the existing life writer, execution broker or risk policy. It is part
of Phase 1 computer agency. It does not certify all EX00–EX23.

## Closed implementation path

1. A successful governed work plan must already have independent final file-byte
   verification before capture. Its file selection alone is insufficient.
2. The compiler admits only one bounded sequential observed form transaction:
   fresh page, up to four replacement text/upload controls, freshly observed
   submit control, bounded completion wait, final page read, saved receipt and
   one required independent exact-byte predicate. Every mutation binds its
   selector from its immediately preceding observation by a fresh explicit label.
3. Upload inputs become `file-list` / `attachments` parameters, each containing
   one to four distinct absolute paths. Source paths, filenames, content, URLs,
   selectors and browser session IDs are not reusable defaults.
4. The ordinary governed browser path still freezes stable file snapshots and
   requests approval for their exact bytes and destination. No transfer code
   manufactures permits or changes the upload risk classification.
   Managed-browser approval now shows the complete snapshot path, byte count and
   SHA-256 in the existing input preview, matching the authorized-browser path.
   A native-filesystem counterexample changes the original during approval and
   requires both the displayed hash and selected snapshot to retain the originally
   frozen bytes. A truncated label cannot replace this reviewable preview.
5. The dedicated owned evaluator allows only its exact nonce loopback page and
   files physically inside its own root. It uses actual CDP file selection.
6. The receiving fixture accepts one exact native multipart POST, parses a
   bounded body and independently hashes every received file. It rejects missing
   or extra files/fields, duplicate text fields, changed bytes and duplicate
   submissions. Receipt text includes received filename, byte count and SHA-256.
7. The work scheduler saves the independently observed receipt, and the life
   verifier checks its bytes. The server observation must also show exactly one
   accepted submission before either positive evaluation input can pass.
8. The eleven-case `browser-upload-replay-v1` result is persisted in the existing
   candidate journal. Prior generic browser or form results cannot approve it.
   Activation, paired-version comparison, failure downgrade, repair and withdrawal
   retain their existing production ownership and gates.
9. A file-selection document closes before its retained snapshots are retired or
   another fixture starts. Cancellation before submission does not become proof
   of delivery, and cleanup does not imply successful task completion.

## Evidence and deliberate supersession

The original rejection test for `tool.browser_upload_files` in the transferable
operation vocabulary is superseded by a dedicated upload compiler/evaluator and
explicit negative tests. Desktop key methods and unspecified program facades
remain outside that vocabulary. This change is an intentional capability-domain
extension, not a removed check hidden by aggregate test counts.

Owned worktree evidence uses `output/execution-v313-*`. The original RED test
proves the prior implementation could not compile the transaction. HTTP tests
cover actual multipart transmission and server-side bytes. The native module
entry checks selection/cancellation without delivery, source capture, evaluation,
three fresh uses, wrong-receipt downgrade, fresh repair/evaluation, three repaired
uses, withdrawal and a file-only transaction. Exact bundled source/native hashes
and the separately packaged host identity are recorded independently. A module
test in an older packaged host cannot certify a release containing these changes.

`LIFE_PRODUCT_UPLOAD_METHOD=1` selects the actual packaged model/UI variant of the
shared form scenario. It verifies the full visible approval before clicking the
real current request/token button, checks fresh file-vector mapping, server hashes,
paired repaired-version metrics, independent persisted upload effects and source
privacy. Each exact owned receipt window closes after delivery to retire snapshots.
It neither closes unrelated windows nor changes the production snapshot budget.

The implementation uses Alicization's existing CDP, snapshot, policy and method
modules. No external source code is copied by this change. The reviewed design
lesson is also visible in browser-use's upload tool and Anthropic's browser-use
tool documentation: a selected file must have explicit source authority, and
selection is not evidence of service receipt. Alicization keeps its stricter
local snapshot and independent-receipt requirements.

## Still open

The v312 actual packaged form attempt is preserved at
`output/execution-v312-form-20261031-pass1/report.json`: its original three uses,
paired repair comparison and first two repaired uses passed, then the third
repaired request failed safely before admission because the provider omitted the
required method id/version. The preceding method-catalogue read had caused the
old planning guard to forbid any correction. The method callback did not run.
The fix preserves all prior read receipts and allows one locally schema-rejected
new proposal to be corrected after known `read` / `read-only` operations. It
offers only that rejected tool for correction; it does not replay an old action
or fill missing method identity itself. Any admitted mutation, external/unknown
effect or published text still closes this correction path. Rejected repair,
cancelled request and untrusted errors retain their existing failure semantics.
The budget is one correction for the entire turn, not one per read. Actual HTTP
counterexamples and current-package replay are required for this change.

Before that form failure, v312's full main regression passed 6441 tests with no
failures and 25 retained skips; its business-form product passed 26 checks and
normal shutdown. The original v311 reviewer failure and v312 form failure remain
evidence. Those passed scopes do not accept the failed v312 package overall or
the later v313 sources.

General browser transactions, arbitrary native GUI method transfer, all adapter
crash matrices, physical user takeover, production Codex/Claude endpoint failures,
cross-version installer acceptance and long-term life continuity retain their
separate work-item evidence requirements. Final qualification must use the
current frozen source and actual packaged product; no broad completion claim is
made by these focused tests.
