# 创作分享的精确引用与授权弹窗竞态

本轮加强同一个人格的创作、执行事实与可见回复之间的连贯性。状态：源码修复与真实服务复核已通过，新的整包体验仍待验证；不宣称 EX00–EX23 全部完成。

## 实际失败

v322 的两轮普通邀请均先由她选择题材，再接受用户邀请、创作并保存作品。独立文件核验和 personal-project 目标已完成，但最终对话变成“模型输出格式异常”。失败记录保留在主工作区 `output/execution-v322-personal-invitation-20261101-pass1` 和 `pass2`。第二次诊断只旁路复制原始响应，未修改原响应、提示、工具结果或服务配置；全部请求 HTTP200。

原因是引用协议要求重抄含换行的句子。为避免服务拒绝带控制字符的 enum，旧协议移除了引用 enum，模型于是合并或拆分段落并输出额外作品段落。实际校验仍要求原文逐字相等，导致第一次审核和一次修复后的审核都失败。不能通过取消内容核验来修复它。

## 实现

`lifeArtifactQuoteReferences` 为当前草稿的待审句子分配 `artifact-quote:1` 等局部编号。响应 schema 只枚举这些编号；审核输入提供编号与完整不可变原文的对应关系。响应中的编号由本轮映射还原后，仍执行原有完整覆盖、作品 obligation/version、真实已验收内容、非空 sourceExcerpt 与语义匹配检查。原始散文和未注册编号均不能代替引用。来源撤销、错误作品版本、伪造来源和缺失审核继续失败。审核策略版本更新为 v81。

这沿用项目现有 `createLifeReplyReviewBindings` 的局部引用机制，未引入另一套人格或执行完成来源。作品仍明确为虚构，不作为真实经历写入记忆。

上传方法的第九个合成表单另暴露测试时序缺陷：专用上传审核器返回“尚无弹窗”后，上传弹窗在文件审核器检查前出现，被后者当作未知写入拒绝。文件审核器现在仅对明确配置由另一审核器负责的 `browser_upload_files` 留下当前 token，下一轮仍由原有精确目标、文件字节及哈希检查授权。默认的未知目标拒绝保持，生产执行权限策略未放宽。
