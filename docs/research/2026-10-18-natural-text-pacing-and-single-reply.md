# 文字节奏、口型过快与重复回复修复

本轮修复两个实际反馈：文字对话时嘴部开合过快；完整回复先出现一次，随后同样的内容又以第二条消息逐字显示，最终才合并。

## 原因与实现

原来的中文呈现周期为 110 ms，约每秒 9 字；每字末尾又强制收口，复韵母和相邻字直接切换嘴形。现在同一可取消游标同时控制文字、角色气泡和嘴部输入：普通汉字 230 ms，短语末字 290 ms；逗号停顿 260 ms，句末停顿 440 ms。相连音节保持开口，复韵母连续插值，相邻字嘴形在 70 ms 内过渡。标点、闭口辅音、中断和实际音频仍有直接控制权；低帧率不能把过渡拖长。

持久化完成和视觉呈现完成原来混在一起。主进程可能先回放完整历史，而远端流式消息没有稳定 ID；聊天历史又只做精确 ID 匹配，不能识别带 `:gwN` 的同一逻辑轮次。现在来源和接收窗口使用同一轮次标识，网关重试归到同一身份。呈现期间，游标前缀覆盖这一行的可见正文；历史数据保留完整内容。结束时更新同一行一次，`stream-end` 不再提前清空显示游标。不同轮次即使文本相同也保留为不同消息。

角色旁的气泡原来优先读取 `structured.reply` 的全文。活动呈现现在显式只读取可见 slices/content，避免它抢先显示完整回复。

职责保持分离：聊天模块拥有呈现节奏和消息提交，历史投影只决定可见行，Live2D 渲染层只投射当前发音输入。嘴部输入不制造声学能量，也不重新触发全身动作。

## 验证范围

回归覆盖早到的持久化回放、网关重试、一个 DOM 气泡逐字更新、结束交接、远端重复结束、内容相同的独立轮次、角色气泡不泄露未呈现正文、整句节奏、标点停顿、复韵母过渡、低帧率追赶、中断和语音优先权。

真实体验使用私有 Windows desktop 上的 Live2D Hiyori 和实际配置的对话服务，通过正常聊天 UI 发起请求，读取 DOM、事件时间和最终 Cubism 绘制参数。不切换用户输入桌面。成品检查的报告、安装器哈希与编译源码对应关系记在 `output/live2d-natural-text-*20261018*` 及发布目录的 `release-provenance.json`。

本次为文字呈现和嘴部节奏的定向回归，不能等同于所有产品功能、长期生命连续性或所有模型的口型验收。呈现仍在结构化回复校验之后开始；尚非供应商网络 token 的即时显示。中文使用拼音近似发音，英语仍按拼写近似；Hiyori 的 open/form 两个参数也不能表达真人全部发音细节。
