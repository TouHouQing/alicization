# Managed browser upload retirement

The managed browser previously cleared all selected-snapshot records before awaiting file cleanup. A locked snapshot could survive on disk without an in-memory retry owner. Closing the window directly did not retire its selected files, and a cleanup failure before native selection also lost its retry owner.

Snapshots are now registered before approval and associated with the exact owned window before native selection. A selection whose native result is uncertain remains retained until that window is destroyed. Only never-selected snapshots or snapshots whose own window is destroyed are eligible for cleanup. Each snapshot has one shared in-flight cleanup promise; its ownership record is removed only after disposal succeeds. Failure remains visible to the caller or error observer and can be retried by a later close. This does not delete the user's source file, declare server receipt, or replay a selection.

One live window retains at most eight selected snapshots and the runtime retains at most sixteen snapshots including failed cleanup. Capacity rejection occurs before copying another file or dispatching native selection. Every individual snapshot retains the existing byte budget.

The original runtime failed three new RED cases: explicit close, host window close, and denied-selection cleanup. Five final retirement tests use real bounded snapshots and file reads, with a mocked browser transport and injected cleanup failure. They cover retry, concurrent close, uncertain native selection, capacity rejection, original-file preservation, and final removal. A four-file composition passed thirteen tests including the existing real isolated Chromium DOM regression. These tests do not establish end-to-end network upload receipt, crash recovery or a durable owner manifest. The first Node typecheck exposed a test union-narrowing error; it was corrected before rerunning checks. Primary integration is pending.

The three reviewed files were selectively merged with v111 hash guards and original backups. Primary composition passed eight files / 124 tests, Node types/build pass88. A subsequent isolated real Chromium test used CDP `DOM.setFileInputFiles`, changed the source after selection, and sent the selected `File` to an owned localhost endpoint. Both the page and server reported exactly the approved snapshot hash, byte count and UTF-8 contents; the edited source remained unchanged. Its three-test file passed twice and Node types passed after correcting browser-only expressions in the Node test project. The test was selectively merged with the v112 source hash guarded. This proves transport of the approved bytes in that controlled scenario, not a generic commercial service receipt or crash recovery.
