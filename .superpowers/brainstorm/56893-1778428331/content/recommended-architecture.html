推荐架构：单一演出总线

核心原则：`心智治理` 只决定“她为什么说、该说什么、说话时是什么状态”；`具身导演层` 负责把这些信息变成一条统一时间线，再由声音、口型、表情、动作各自执行。

目标层级

1. Mind Authority

Main Runtime

保留你现在最强的部分：`mind-turn-v1`、truth discipline、dialogue governance、digital-life spine。它只产出“被治理后的回复事实”和“当前生命状态”，不直接操心具体怎么张嘴、眨眼、抬手。

2. Embodiment Director

新增权威层

把 `reply + thought-derived performance + speechTimeline + digitalLifeSpine + resident state` 收束成统一的 `performance script`。这层才是 Live2D/语音演出的单一真相来源。

3. Execution Drivers

可替换执行器

拆成 4 个执行器并行消费同一脚本：`Speech Planner/TTS`、`LipSync Driver`、`Face Driver`、`Motion Driver`。它们不再彼此猜测，而是共享同一时序、同一 cue、同一 interruption policy。

4. Telemetry & Repair

回流层

采集真实播放时长、TTS 首包延迟、打断点、mouth drift、表情动作丢失、renderer failure，回流给 director 和 runtime，形成“越用越稳”的闭环。

一条标准闭环

User turn / quiet presence trigger
Alicization Runtime 产出 `mind-turn-v1`
Embodiment Director 产出 `performance script`
Speech Planner 分段、优先级、可打断策略
TTS 输出 audio + phoneme/energy metadata
LipSync / Face / Motion 同步消费
Playback telemetry 回流修正 resident state

重点不是“模块更多”，而是每一层只做一件事，并且上层不直接越级操作下层。

当前架构最需要修正的点

  • 并行派发过强：`presence dispatcher` 现在更像是把 performance/tts 平行扔给多个 controller。
  • 统一时序不足：`speechTimeline`、`digitalLifeEnvelope`、实际音频播放、Live2D 口型循环之间有抽象，但还没有单一 timeline authority。
  • 状态回流不完整：真实播放、打断、掉帧、动作失败没有充分反向塑造下一次 resident performance。
  • Renderer 抽象偏晚：Live2D/VRM 差异更多在执行端兜底，而不是在导演层先收敛。

为什么这条路适合你现在的仓库

  • 不推翻心智层：保留 `Alicization` 的 runtime / governance / truth discipline 资产。
  • 先强化 Live2D：一期只把 Live2D 做成主栈，VRM 以后作为第二执行器接入。
  • 先适合桌宠形态：最适合你当前要的按钮/聊天框交互，不被全双工音频系统拖死。
  • 天然支持以后升级：后续加 VAD、半双工、全双工时，只要增强 Speech Planner 和 interruption protocol，不需要推倒整套人格层。
