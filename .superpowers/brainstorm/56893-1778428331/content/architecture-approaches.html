数字生命长期架构路线对比

目标已经明确：产品表现像单人数字伴侣，但底层骨架要能承载具身 agent；一期以 Live2D、桌宠式交互、中文优先、生命感和低延迟为主。

路线 A

继续强化现有双层拼接

保留现在的 `mind governance -> presence dispatcher -> speech/performance runtime` 结构，只做局部加固。

生命感
实时性
开发速度
可维护性
优点：最省改动，短期能继续堆功能。
风险：心智层和具身层会继续出现“有状态但不同步”的问题，后面做实时打断、动作优先级、表情过渡会越来越难。
推荐路线 B

建立单一“演出总线”

把 `mind-turn` 的最终结果收束为统一的 `performance script / embodiment timeline`，再分别驱动 TTS、口型、表情、动作。

生命感
实时性
开发速度
可维护性
优点：最适合你现在这个仓库，因为心智层已经很强，只差一个“具身权威层”把 reply、prosody、mouth、face、body 真正绑定在同一时序里。
风险：需要一次明确的中层重构，不是纯补丁。
路线 C

外置成多进程数字生命平台

像 `N.E.K.O` 一类架构那样拆成 agent/server/client/tts/animation 等多个服务，本仓库变成前端壳。

生命感
实时性
开发速度
可维护性
优点：平台化强，后续接 Web、移动端、远程服务更舒服。
风险：对你当前“本地活着”的目标来说太重，短中期会把大量精力花在基础设施而不是生命感闭环。

我建议的闭环形态

不是 “LLM 回一句话，然后各模块自己猜该怎么动”，而是先生成一条受心智治理约束的演出脚本，再由多个执行器消费同一条时间线。

1. Main Runtime 产出 `mind-turn-v1`
2. Embodiment Director 产出统一 `performance script`
3. Speech Planner 产出 prosody / 分段 / 可中断策略
4. LipSync Driver 消费音频 + phoneme/energy/viseme
5. Face Driver 消费 emotion / facial cue / micro-expression
6. Motion Driver 消费 action cue / posture / idle state
7. Telemetry 回流，修正下次演出与实时策略

关键判断

你现在最值钱的资产：`Alicization` 的 mind/runtime/governance 已经足够深。

你现在最大的结构问题：具身层仍然偏“并行派发”，而不是“统一编排”。

如果继续沿路线 A 迭代，你会越来越常见这些问题：表情和语音错位、动作抢占不稳定、实时打断后状态悬挂、不同渲染器行为不一致、从聊天到常驻陪伴时的 resident state 很难统一。
